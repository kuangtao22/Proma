# 画布生产

画布不是普通对话的替代品，也不是一个放大版附件列表。它用于承载多个可独立评审、复用、运行和继续衍生的产物，以及这些产物之间的关系。

本 Skill 负责语义理解和生产编排。真正的读取、创建、更新、运行、授权和事务仍由 Proma 的 `canvas_*` 工具完成。

## 什么时候使用

以下任务通常适合画布：

- 创建或迭代网页原型、交互页面、桌面端与手机端视觉稿。
- 创建产品套图、系列海报、角色设定、漫剧分镜等多个关联图片产物。
- 把需求、程序规划、信息架构、设计规范等拆成可持续维护的文档节点。
- 基于已有文档、WebView 或图片继续衍生新页面、新版本或新产物。
- 用户明确提到画布、节点、连线、引用某个画布产物或要求把结果放进画布。

以下任务不要强行转入画布：

- 用户明确要求修改项目中的 HTML、React、组件、样式或其他代码文件。
- 一次性问答、短文本润色、简单分析或不需要长期维护产物关系的任务。
- 仅仅因为用户说了“首页”“设计”“视觉”“图片”等词，但实际交付仍然是项目代码。

如果用户想要可视化产物，但无法判断他需要可交互 WebView、静态图片设计稿还是直接修改代码，只询问一次，提供“创建 WebView 原型”“创建图片设计稿”“继续普通 Agent”三个选项。用户已经明确产物类型时直接执行，不重复询问。

## 工作原则

1. 先理解完整任务，不按单个关键词触发。
2. 先读取当前画布和明确引用，再决定是否创建新画布或节点。
3. 一个可独立评审、复用或迭代的产物对应一个节点。
4. 有连线表示存在明确关系；没有关系的产物保持独立，不为了画面整齐强行连线。
5. 优先局部更新已有节点，保留稳定节点 ID 和版本历史，不无故重建整套内容；确需重建时先建立并验证新链路，再删除旧节点。
6. 先建立可评审的结构和内容，再按用户意图运行需要计算或付费的节点。

## 普通 Agent 与 Canvas Agent

普通 Agent 负责跨画布选择和整体编排；当前会话位于 Canvas Agent 节点时，画布身份已经由系统固定，只处理自身画布中的当前分支。

任务需要独立角色长期承接分镜、视觉、文案或其它分支时，普通 Agent 自行调用 `canvas_create_agent` 创建 Canvas Agent 节点，并根据真实输入建立关系；不得声称没有创建能力，也不得把这一步转交给用户手工完成。当前会话位于 Canvas Agent 节点时，不再创建下级 Agent，由当前 Canvas Agent 直接完成自身分支。

Canvas Agent 开始任务时，先通过 `canvas_get_context` 获取直接输入节点，再用 `canvas_read` 读取真实内容和关系。不得把连线只当作视觉装饰，也不得仅凭节点标题猜测正文。任务要求生成脚本、首尾帧配置、文档或原型时，由当前 Canvas Agent 直接创建或更新下游产物，并建立准确关系；不得只输出一份“建议用户之后创建”的清单。

不得把普通 Agent、协作会话或当前会话伪装绑定为 Canvas Agent 节点。不得要求用户在主会话与 Canvas Agent 之间反复复制任务；系统已提供的直接输入节点就是本轮生产入口。Canvas Agent 不能使用 `canvas_manage` 创建、关联或切换其它画布。

## 标准工作流

### 1. 获取权威上下文

先调用 `canvas_get_context`，确认：

- 当前会话关联了哪些画布；
- 默认和最近活动画布；
- 用户本轮明确引用了哪些节点；
- 当前是 `plan` 还是 `execute` 权限上限。

已有合适画布时直接复用，不要要求用户再次创建。只有没有可用画布，并且用户已明确选择画布产物时，才使用 `canvas_manage` 创建并关联画布。

### 2. 读取必要节点

存在明确引用、需要继续已有产物或依赖上游内容时，使用 `canvas_read` 读取目标节点。只有关系会影响本次判断时才读取邻接节点，不扫描无关画布或全部节点。

读取后以返回的当前 revision、内容 revision 和权威关系为准。内容被截断时不要假设未返回部分；缩小范围后再次读取。

### 2.1 全量图片视觉核对

用户只要求“核对”“检查”或“评审”图片一致性时，核对只读：

1. 先使用 `canvas_list_nodes` 并设置 `kind=image`，分页枚举同一 revision 下的全部图片节点。
2. 对存在当前正式采用图片的节点，再使用 `canvas_inspect_images` 每批最多读取四张缩略图。
3. 从表现媒介、人物外观、服装道具、场景时间、色调光线、镜头构图、文字和品牌元素等维度汇总一致、异常与无法判断节点。
4. 全部页面和批次完成后才能声称“已核对所有图片”；中途失败时说明已检查数量、未检查数量和原因。

不得只比较提示词后声称已经看过图片，也不得使用画布截图或当前可见节点推断全量结论。用户未明确要求修正时，不更新提示词、不调用 `canvas_run_nodes`、不采用候选，也不自动创建报告文档。模型不能消费图片内容时，明确说明只能检查提示词与配置，不能冒充视觉核对。

用户明确要求统一提示词时，只更新视觉异常节点，不自动生图。用户明确要求立即重新生成异常图片时，才更新异常节点并一次调用 `canvas_run_nodes`；审批和候选验收边界保持不变。

### 3. 规划产物图

创建前先在内部确定：

- 本次有哪些可独立交付物；
- 每个交付物对应什么节点类型；
- 哪些节点需要关系，关系表达什么含义；
- 哪些节点只需保存，哪些节点需要立即运行。

简单任务可以直接创建单节点。多页面、多张套图、多段分镜或多份规划必须拆成多个节点，禁止把所有产物塞进一个巨型节点。

普通创建不要主动提供 `position`。由 Proma 根据来源关系和真实节点尺寸紧凑排布；只有用户明确要求特殊版式时才提供坐标，Host 仍会校验重叠、有限数值和异常距离。

### 4. 创建或更新内容

已有授权本地图片不是生图提示词。需要把 Agent 当前工作区、项目目录、附件或其它已授权路径中的现有图片作为画布参考时，使用 `canvas_import_image`。导入成功后，原图会立即成为该图片节点的正式采用版本，可直接被下游节点引用；不得要求用户拖入或上传到原生 Canvas，也不得用 WebView 代替图片参考节点。

使用 `canvas_create_artifact` 创建含真实内容的产物：

- `document`：提供完整 Markdown，适合需求、规划、故事大纲、设计规范和说明文档。
- `webview`：提供可独立预览的完整单文件 HTML；根据目标选择 `desktop` 或 `mobile`。
- `image`：提供可直接用于生图的完整提示词，而不是模糊摘要。

从已有节点衍生时，同时提供 `sourceNodeId` 和准确的 `relation`。不要把 Markdown、HTML 或图片提示词正文交给 `canvas_apply_changes`。

修改已有文档、WebView 或图片提示词时，先读取当前版本，再使用 `canvas_update_artifact` 做局部更新。不要为了修改一处内容重新创建整个节点。

需要替换损坏流程或调整节点职责时，先创建新节点、补齐关系并确认新链路可读取和可执行；只有这些验证完成后，才通过 `canvas_apply_changes` 显式删除旧节点。禁止先清理旧流程，再临时发现新节点或工具不可用。

`canvas_apply_changes` 只用于结构性画布修改，例如新增或调整节点、边和布局，不负责保存产物正文。

### 5. 按需运行

WebView 创建后即可预览，不要为 WebView 调用 `canvas_run_nodes`。

图片节点的创建或提示词更新只保存配置。只有用户明确要求立即生成图片时，才调用 `canvas_run_nodes`。该工具仍需要单次审批，不能因为 Skill 已加载就视为用户已经批准付费运行。

运行后根据返回状态说明哪些节点已启动、排队、失败、阻断或暂不支持。不要把 `unsupported` 描述成已经生成。

图片生成成功后先形成待验收候选。未获得采用授权时只汇报“候选已生成”，不得描述为已经正式替换；当前卡片和下游任务继续以已采用版本为准。用户明确采用后，再汇报采用数量、保留旧版数量和需要重新检查的下游节点。

### 6. 复读与继续迭代

创建、更新或运行后，按需再次读取受影响节点，确认版本和关系。后续修改优先针对用户指出的节点和局部内容，不自动重做用户已经接受的其它产物。

## 节点关系语义

关系必须表达真实业务语义：

- `association`：两个产物相关，但没有明确方向性依赖。例如同一活动的两张独立海报。
- `reference`：目标在创作或判断时参考来源，但来源变化不必然要求目标重做。例如视觉稿参考品牌规范。
- `depends-on`：目标依赖来源才能成立，来源变化可能要求重新检查目标。例如页面原型依赖需求文档。
- `derives`：目标是从来源直接衍生的新版本或新产物。例如桌面首页衍生手机首页、角色设定衍生分镜。

不能确认关系时保持独立，或在关系会改变后续执行时再询问用户。

## 典型生产模式

### 产品宣传套图

- 先建立活动目标、品牌约束或文案文档节点。
- 每张需要独立评审或投放的图片对应一个图片节点。
- 图片引用共同规范时使用 `reference`；从同一主视觉延展时使用 `derives`。
- 用户要求立即出图时再批量运行图片节点。

### 漫剧与分镜

- 故事大纲、角色设定和视觉规则分别使用文档节点。
- 每个可独立调整的镜头或分镜使用独立图片节点。
- 分镜依赖剧情时使用 `depends-on`，视觉延续关系使用 `reference` 或 `derives`。

### 交互视觉稿

- 需求、信息架构或设计规则使用文档节点。
- 首页、发现、我的等独立页面分别创建 WebView 节点。
- 桌面端和手机端是独立可评审产物时分别建节点，并用 `derives` 表达适配来源。

### 程序规划

- 需求、架构、任务拆分和验证策略可以分别创建文档节点。
- 只有用户需要可运行原型时才增加 WebView；真实项目代码仍由普通 Agent 工具修改。

## 权限和安全边界

Skill 不授予任何画布权限，也不能扩大当前会话、项目或画布的访问范围。

- `plan` 只允许工具合同认可的新增 idle 结构，不允许创建产物、运行、覆盖、删除或移动。
- `execute` 只表示工具具备执行条件，不代表用户授权了任意副作用。
- 删除或覆盖已有节点、边或内容必须来自用户明确意图；工具要求时传入 `destructiveIntent=explicit`。
- 生图、视频或未来其它可能付费的运行必须遵守相应审批，不得拆分调用绕过限制。
- 工具返回 revision 冲突、访问拒绝或引用失效时，重新读取权威状态后调整方案，不得伪造成功。

## 反模式

- 根据“首页”“设计”等关键词直接创建画布。
- 已有关联画布时仍要求用户新建画布。
- 为三个页面只创建一个包含全部页面内容的 WebView 节点。
- 为了展示关系给所有节点随意连线。
- 用 `canvas_apply_changes` 写入 Markdown、HTML 或图片提示词正文。
- 已有授权参考图时要求用户拖入 Canvas，或创建 WebView 假装图片参考节点。
- 需要独立 Canvas Agent 分工时要求用户手工创建节点。
- 重建流程时先删除旧节点，尚未验证替代链路是否可执行。
- 更新一个节点时重建整个画布或覆盖无关节点。
- 创建图片节点后在用户未要求立即生图时自动运行。
- 把候选图片描述成已经正式替换，或在未获得采用授权时默认覆盖旧版。
- 把 WebView 当成需要运行的生成节点。
- 把 Skill 当成权限来源，绕过工具错误、审批或破坏性意图检查。

## BDD 场景

**场景：用户明确创建网页原型**

- Given 用户说“在画布中创建桌面和手机两个首页原型”
- When Agent 读取当前画布上下文
- Then 创建两个独立 WebView 节点，使用对应设备预设并建立合理衍生关系，不重复询问产物类型

**场景：普通代码修改**

- Given 用户说“修改项目里的 React 首页”
- When Agent 判断交付物是代码文件
- Then 继续普通 Agent 开发流程，不创建画布或空白节点

**场景：多张产品套图**

- Given 用户要求基于品牌规范制作三张宣传图
- When Agent 规划产物图
- Then 品牌规范和三张图片使用可独立维护的节点，图片引用规范；仅在用户要求立即生成时运行图片节点

**场景：继续已有节点**

- Given 用户引用现有首页 WebView 并要求衍生“发现”和“我的”页面
- When Agent 读取引用节点
- Then 创建两个独立 WebView 节点并用 `derives` 连接来源，保留已有首页节点不变
