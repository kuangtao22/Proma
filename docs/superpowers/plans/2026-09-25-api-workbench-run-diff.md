# 接口工作台 B11：响应差异比较（实施计划）

> 前置：阶段 A 的「尚未交付」清单里，**JSON 类型断言**已在 B10 交付，本轮收口另一项 **响应差异比较**。
> 状态：**已交付**（提交信息 `接口工作台（B11）：响应差异比较`，验收记录见第 5 节）。

## 1. 要解决的问题

改完参数或后端发版后，最常问的两个问题是「这次和上次差在哪」和「我这次改动到底影响了什么」。现在只能靠肉眼对两屏 JSON。需要的是**把两次运行放在一起给结论**：状态码/大小/耗时/内容类型/响应头/断言结论有没有变，正文哪几行变了。

## 2. 设计

- 纯函数 `diffApiRuns(baseline, candidate)`（渲染层模型）：结构化对比 + 正文逐行差异，可单测、不发网络、不碰主进程。
- 结构化对比：状态码、方法+URL、跳转数、内容类型、原始/解码字节、总耗时、事件数量与结束原因、用例身份、断言通过数；**响应头**按名称合并重复值后给 added/removed/changed；**断言**按 id 对齐给结论变化。
- 正文差异：两侧都取**默认脱敏投影**（绝不 reveal），逐行 LCS。为守住界面性能：两侧行数都 ≤400 时才做逐行比较；超出只报「超过逐行对比上限」而不伪造差异；输出只保留变化行（去掉共同上下文）并再截断到 200 行。
- 交互：运行头部「设为对比基线」记录当前运行，「与基线对比」在选中另一条运行后可用；对比在弹层里并排展示，两侧都标注请求名与时间。

## 3. 明确不做

- 不 reveal 原始正文：对比永远基于脱敏投影，被遮罩的秘密不会出现在差异里。
- 不做字符级 diff、不做跨请求批量对比、不落盘保存对比结果。
- 不引入 diff 依赖：行级 LCS 自己实现（受上面上限约束，规模有界）。

## 4. 验收标准

1. 单测：相同运行判一致；状态码/耗时/大小/内容类型变化各自被标出；响应头 added/removed/changed；断言按 id 对齐给结论变化；正文逐行差异只列变化行；超过行数上限时明确报「无法逐行对比」而不是给出错误差异。
2. 界面 smoke：设为基线 → 打开另一条运行 → 「与基线对比」弹出对比面板，显示变化项与「正文相同」结论。
3. 定向回归、`bun run typecheck`、`bun run electron:build` 通过；真实 Electron 端到端保持通过（本增量不涉及主进程与传输）。

## 5. 已交付与验收记录（2026-09-25）

已交付行为：

- 运行头部新增「设为对比基线」与「与基线对比」（基线与当前运行相同时禁用）。对比时读取两次运行的**默认脱敏投影**（绝不 reveal），在弹层里并排展示。
- 结构化对比：状态码、方法 URL、跳转数、内容类型、原始/解码字节、总耗时、事件数量与结束原因、**用例（显示解析后的用例名，而不是 caseId）**、断言通过数；响应头按名称合并重复值给出 新增/删除/变化；断言按 id 对齐给出结论变化（`未执行`/`通过`/`失败`）。
- 正文差异：两侧预览相同直接给「正文相同」；都 ≤400 行时做行级 LCS，只列变化行（`+`/`-`，最多 200 行）；超过上限明确报「超过逐行对比上限」而不伪造差异。
- 为区分同一秒内的两次运行，运行标签带运行号尾段（`请求名 · 时间 · 尾号`）。

已知边界：断言差异只能显示断言 **id**（运行记录保存的是断言结果，不含 `kind`/`path`，与 B9 的限制同源）；对比不做字符级 diff、不落盘、不跨请求批量比较。

过程中踩到的坑（已修正）：界面 smoke 的窄 Pane 截图会把窗口调小且不还原，后续步骤都在紧凑布局下运行——紧凑布局里关掉历史面板后响应区不再渲染，所以断言「看不到 200」。修法是回到对比步骤前先把窗口恢复为宽布局；另外同一请求名的历史行 aria-label 完全相同，必须按行内文本（用例名/状态）挑行，否则会点到同一条运行。
