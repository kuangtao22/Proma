# Agent 服务器运维访问：改进建议与验证记录

日期：2026-09-21

状态：用户批准的方案已实现；最终自动化与隔离链路验收通过，详见[实施与验收记录](../plans/2026-09-21-server-ops-agent-access.md)。下方「实施前验证与证据」为历史调查，不代表最终实现状态；真实 GUI 点击与外部模型自主选工具仍未验收。

## 结论

推荐采用「按会话保存的短时只读授权 + 常驻授权入口 + 有界读取队列」，并提供显式的「运维只读模式」限制本轮工具集。授权继续精确到连接身份、数据库、表、行读取与 SQL 查询；项目只用于组织资源。

实施前发现切换聊天撤权、会话授权互相覆盖、同数据源并发直接报忙与取消错误归因不准确的问题，已按下方方案修复。最终全仓 7,382 项测试通过，隔离真实 SSH/SQLite 链路的上述问题均通过回归；不能将这些结果表述成“整个 Agent 已被安全沙箱隔离”。

## 备选方案

| 方案 | 对用户的影响 | 安全与工程取舍 |
| --- | --- | --- |
| A：保留单槽授权，仅补入口和错误提示 | 能找到授权入口，但切任务仍需重复授权，后台任务仍容易中断 | 改动小，无法解决多任务使用的主要问题 |
| B：会话级短时授权，配合受限运维模式（推荐） | 授权后可以切换界面、连续提问；权限范围与有效期随时可见 | 必须补齐主进程生命周期撤权、调用取消和跨会话隔离；改动可限定在运维与运行工具选择边界 |
| C：项目永久自动授权 | 操作最少 | 新连接、其他任务和未来运行容易获得用户未逐项确认的访问；不推荐 |

## 推荐方案的具体行为

### 1. 用户始终看得见权限

- 聊天输入区与运维连接详情顶部显示同一份主进程授权事实，例如「运维只读 · 车本本 / chebenben · 结构 · 剩余 24 分钟」。状态由授权事件更新，不轮询数据库。
- 没有授权时，工具返回结构化状态与固定下一步；聊天显示“管理运维授权”入口。入口只打开编辑器，不自动授予权限，不向模型泄漏尚未授权的连接目录。
- 保持「结构 → 行数据 → SQL 查询」三层能力。新增库表、打开行读取或 SQL 时，用户看见精确范围后提交。
- MySQL 没有实例或库范围时在原位置提示并禁用保存；按钮统一叫「Agent 只读授权」，保存后的数量以徽标显示。
- SSH 只读概览需要已连接的服务器。明确提示用户连接状态，避免模型用旧 `server_connect` 作为数据库只读工具的通用前置步骤。

### 2. 会话授权与运行取消分别管理

- 主进程按真实 `sessionId` 保存只读授权，字段包含资源范围、配置指纹、授权代次和固定到期时间；仍仅在内存中保存，默认有效期建议为 30 分钟，不因调用自动延期。
- 扩权、缩权、重新保存和到期后的重新授权都生成新的单调递增 revision，立即取消该会话旧 revision 的排队及在途请求，旧回执不得发布或恢复授权。其他会话的只读 revision 不受影响。
- 不再因切换聊天或运维页签撤销只读授权。不同会话各自独立，建议最多 8 个有效会话，每个继续沿用最多 32 个资源的既有限制；达到上限时明确提示管理已有授权，不静默替换其他会话。
- 显式撤权、有效期到达、会话归档/删除、连接删除或身份/凭据变更、应用退出会使相应授权失效。由主进程事件处理，不能只依赖当前打开的 Renderer 标签。
- 每次用户发起的运行获得绑定 `sessionId + runGeneration + accessRevision` 的调用身份。停止该次运行立即取消在途调用并废弃该运行身份；新的用户消息只能在仍有效的会话授权内重新取得身份，后台来源不能借用。
- 运行身份只能由主进程/Orchestrator 的可信闭包注入，不能作为模型可填参数或 Renderer 可提交的运行身份。Renderer 授权 DTO 仍可指定目标会话，但主进程必须重新验证其资格并自行生成 revision。
- 入队、出队、执行前与返回前均同步检查 `expiresAt <= Date.now()`，不能仅依赖到期计时器。另用宿主单调时钟限制最长时长，时钟回拨不能延长授权；系统恢复后先复核有效期再接受新调用。
- 旧 SSH 操作授权继续保持单槽，与全部只读授权保持现有的全局互斥：授予旧操作授权会撤销所有只读授权，授予只读权限会撤销旧操作授权。提交前显示会被撤销的授权数量与会话，不能静默替换。这个兼容选择意味着服务器操作模式仍会打断只读访问，但普通只读任务之间不再互相覆盖。
- 会话切换守卫改为仅撤销离开会话的旧 SSH 操作授权，不能直接删除整个守卫；显式“撤销该会话全部权限”仍同时清理两类授权。旧 SSH 写操作继续逐次审批，不将只读访问升级成命令执行或文件写入。
- 自动化、委派、Canvas/Design 内部运行和外部触发仍不继承。用户可见的探索分支保留现有独立授权能力，但不能继承父会话授权；本轮未发现父权限继承漏洞。
- 撤权阻止新的读取与尚未发布的结果；已经交给模型的历史内容无法通过撤权收回，界面应准确表达这一边界。

### 3. 连续读取可等待、可取消、错误可解释

- 在现有数据服务处统一管理用户面板与 Agent 请求；每个数据源串行执行，沿用全局最多 3 个实际读取的上限。
- 建议每源最多等待 8 个请求、全局最多等待 24 个、等待时间最多 5 秒。排队前、出队后与返回前都复核授权和连接身份；取消、撤权、过期或配置改变时立即移出队列。
- 每源 FIFO，跨源按轮转调度；每个 Agent 会话最多等待 8 个请求，避免单任务占满全局队列。5 秒从入队时开始计算，到期/取消/完成都释放计时器与 abort listener。
- 返回明确的排队/超时/资源变更状态；不让模型因 `BUSY` 反复探测，也不自动重跑已经开始的 SQL。
- 所有只读方法统一接收本轮 AbortSignal。目前 SQL 已能中断实际远端执行，表目录/结构等其他读取主要依靠返回前检查阻断数据；应同步接通它们的主动取消以减少资源占用。
- 修正查询错误归因：在执行失败分支再次检查授权与调用取消状态，再归一化底层错误。撤权返回 `SERVER_OPS_AGENT_ACCESS_CHANGED`，用户取消返回 `SERVER_OPS_SQL_CANCELLED`；审计使用相同原因。
- Agent 默认继续实时读取。此阶段不引入新的 Agent schema 缓存，避免把界面缓存策略与模型读取的新鲜度混为一谈。

### 4. 运维只读模式提供明确的工具边界

- 普通编码 Agent 的 Shell、文件、MCP 等能力不受运维库表白名单约束。即便运维工具严格只读，拥有其他凭据和工具的 Agent 仍可能经其他路径访问资源。
- 新增显式的运维只读运行模式：本轮工具只注册已批准的 `ops_*` 读取能力，不注册 Shell/PowerShell、文件读写、浏览器、任意 MCP 或委派工具。选择与校验均在运行宿主完成，分派层也必须拒绝白名单外名称，不能只隐藏模型工具描述或依靠提示词。
- 所有旧 `server_*` 工具也不在运维只读模式的白名单中，包括连接、命令、Docker 和文件操作。模式与工具集在本轮 generation 启动时冻结；切换模式或恢复会话时终止旧 generation、取消其请求并重建工具集，不复用普通编码 runtime 的工具实例。
- 该模式获取的内容仍会发送给所选模型，敏感列遮罩不能保证所有业务文本都已匿名；授权界面继续明确说明。
- 远端名称、注释和行值按不可信数据处理，不能用它们扩大权限。用合成提示注入样本测试越界工具分派，并与真实模型测试分开报告。
- 第一阶段不改变普通编码模式的权限语义；需要服务器写操作时进入独立操作流程，继续逐次审批。

### 真实执行链路

使用临时数据库、临时业务配置目录、独立 Electron userData 和回环 SSH，运行生产代码的工具 `execute` → 会话 Facade → DataService → Electron utility process → SSH exec → Python → SQLite。授权存储、身份校验、数据服务、数据源文件与审计文件均使用正式实现；会话目录、主机元数据和工具注册器为夹具，未调用外部模型、未经过真实 UI 的授权 IPC。

单进程临时审计/配置使用无竞争事务适配，不把此次结果宣称为多实例文件锁验证；主进程 IPC 由上述独立测试覆盖。

最终结果：**安全断言通过，同时保留 4 项流畅性/错误分类发现**。21 次 SSH exec；撤权与用户取消均收到真实 TERM（合计 2 次）；44 条严格审计记录。

已实测：

- 无授权、越库、越表、伪造 session 参数、缺少行/SQL 权限时，在远端执行前拒绝。
- 目录只暴露已授权表；真实行中的测试密码值被遮罩。
- 合法 SELECT 成功；写入、多语句、敏感列和未授权表拒绝。
- 会话 B 无法复用 A 的授权；自动化/委派/外部来源不注册 facade。
- 10 次连续表结构读取全部成功；本机回环环境 P50 76 ms、P95 92 ms。该数据不代表生产网络、MySQL 或模型思考延迟。
- SQL 执行中撤权后 25 ms 内工具返回拒绝、真实远端收到 TERM，同一连接随后可再次查询。
- 表结构已在远端生成、回包被夹具延迟时，撤权后结果不能交给模型。
- 用户取消信号到达远端，取消后同连接查询成功。
- SQLite 文件路径改变时旧授权失效；审计不含行值与 SQL 正文；测试前后数据库字节完全一致。

### 确认的问题

| 问题 | 证据 | 用户影响 |
| --- | --- | --- |
| 同库并行读取直接冲突 | 两个真实工具并发读取，结果为一个 success、一个 `SERVER_OPS_DATA_SOURCE_BUSY` | 用户面板与 Agent 同时查看时容易中断；模型需要重试 |
| 授权被界面切换或其他任务替换 | 真实 AccessStore 与会话切换守卫复现 | 用户切走查看其他任务后，原 Agent 失去读取权限 |
| 撤权/用户取消错误归因丢失 | 真实 runtime 均先抛 `SERVER_OPS_DATA_CANCELLED`，查询审计 catch 未重新检查授权/取消 | 工具与审计无法准确说明中止原因；现有 mock 迟到成功用例未覆盖该拒绝路径 |
| 授权入口只在项目列表 | 真实组件 `ServerOpsWorkspace` 仅在项目页 toolbarActions 装配入口 | 已进入数据库工作台时难以找到给 Agent 授权的位置 |

## 改动影响与实施验收

组件/controller 的 9 项测试通过（已包含在上述 265 项中，不重复累计）。GUI 验收未通过验证：浏览器控制返回认证不可用；原生备用路径的临时夹具出现共享类型与 React 组件同名导入冲突，随后窗口控制长时间无响应并被中断。临时 Electron、Vite 与界面夹具已清理，没有实际键盘/宽窄界面/完整点击链路证据。静态代码与组件测试可证明草稿隔离和状态回执防护，不能替代真实焦点、点击命中与 UI→IPC 全链路验证。

改动涉及 shared 授权合同、主进程授权与生命周期事件、preload 事件桥、Renderer 授权入口与状态、Agent 工具选择、数据服务队列和取消链路。需保持四层 IPC 一致，重点回归普通编码、旧 SSH 写操作、Automation、Delegation、探索分支及会话恢复。不要移除全局会话守卫而同时让旧 SSH 操作权限不再撤销，应分别处理读授权和操作授权。

性能方面，授权是有界内存查找，状态通过事件推送；每次读取仍复核真实配置身份。单个到期计时器或最早到期调度即可，不逐会话高频轮询；授权到期必须同时取消在途与排队请求。队列只保存有界请求元数据，实际数据库并发上限保持 3；不缓存行值或 SQL 结果，不新增依赖。

实施后的验收矩阵必须覆盖：A/B 并行只读会话互不覆盖、切界面不打断只读；切走会话仍撤销旧 SSH 操作授权；旧操作/只读模式全局互斥且提交前清楚提示；到期/撤权/归档/删除/配置变化时在途与排队请求失效；扩权/缩权/保存/续期都废弃旧 revision；计时器延迟、系统恢复与时钟变化不能放行过期调用；旧回执不能复活权限；SQL 拒绝路径的授权/取消错误码准确；同库并发按 FIFO 有界等待、跨源轮转、单会话配额与 listener 清理；主进程伪造 IPC/运行身份拒绝；受限运维模式中 Shell/MCP/委派及所有旧 server_* 不注册且不可分派，切模式/恢复时旧工具实例不复用；深浅主题、窄面板、键盘焦点与保存失败恢复。

本轮没有连接用户的真实数据库、没有授予真实 Agent 新权限、没有替换或重启现有客户端。新方案仍需实施后重新运行上述验收；本次通过的结果只证明当前被测路径。
