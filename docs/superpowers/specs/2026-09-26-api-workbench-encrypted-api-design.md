## 1. 结论与取舍

加密接口要解决三件事：**发送前变形**（派生、签名、加密）、**收到后还原**（解密，再交给断言/提取）、**密钥不进记录**。做法是在工作台里加三层结构：

```text
公共配置（统一管理）        每个接口（只做选择）          发送与接收（按方案执行）
变量与密钥 12 条      →    选一套签名与加密方案      →   派生 → 签名 → 加密
签名与加密方案 4 套         + 可选覆盖项                 解密 → 断言 / 提取
公共请求头 / 参数 / 鉴权
```

| 方案 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| 方案公共、接口只选（本方案） | 算法与模板是系统级约定，改一处全体一致；可审计、可 diff | 要新增公共配置实体与引用检查 | **采用** |
| 每个接口各自定义加解密步骤 | 单接口自由度最高 | 同一套约定被复制 N 份，必然漂移；改一次要改几十处 | 否决（用户已否） |
| Postman 式 Pre-request Script（任意 JS） | 覆盖任何非标算法 | 脚本能读凭据、能出网、能写盘；Agent 能改脚本绕过审批；不可审计 | 否决 |
| 受限表达式 DSL（md5/hmac/sortedJoin 等原语） | 覆盖国内常见"拼串签名" | 需要单独设计求值器与错误信息；当前样例不足 | 暂缓，作为 P3 逃生舱 |

## 2. 术语与数据模型

### 2.1 作用域（变量的四层）

| 作用域 | 含义 | 例子 |
| --- | --- | --- |
| 工作区级 | **整个项目共用一份**，跨所有集合、所有接口生效 | 公司统一的 `X-App-Version` |
| 集合级 | 只在某个集合内生效 | 「后台接口」专用 `ts` |
| 环境级 | 同一变量名，每个环境各存一份值 | `baseUrl`、`appSecret` |
| 接口级 | **不存值**，只存"用哪套方案"+ 可选覆盖项 | 「保存 AI 能力」→ 后台签名 |

取值顺序：**接口覆盖 → 运行时变量 → 环境 → 集合 → 工作区**。接口上必须能显示"这个值最终来自哪一层"，避免"改了不生效"。

### 2.2 签名与加密方案（`ApiCryptoProfile`）

```ts
interface ApiCryptoProfile {
  id: string
  name: string                    // 例如「车本本-后台签名」
  description: string
  scope: 'workspace' | { collectionId: string }   // 默认工作区级
  appliesTo: 'all' | 'test' | 'production'        // 适用环境，默认 all
  requestSteps: ApiCryptoStep[]   // 发送前，按数组顺序执行
  responseSteps: ApiCryptoStep[]  // 收到后，按数组顺序执行
  revision: number
  updatedAt: number
}

interface ApiCryptoStep {
  id: string
  kind: 'derive' | 'sign' | 'encrypt' | 'decrypt' | 'verify'
  enabled: boolean
  algo: string                    // 见 §2.3
  /** 密钥/IV 只引用变量名，永不内联值。 */
  keyRef?: string
  ivRef?: string
  template?: string               // 待签/待加密内容，支持 {{method}} {{path}} {{query.sorted}} {{body.raw}} {{body.sha256}} {{timestamp}} {{nonce}}
  source?: 'body' | 'query' | 'response-body' | 'response-field'
  target?: { in: 'header' | 'query' | 'body'; name: string }
  encoding?: 'hex' | 'base64' | 'raw'
  onFailure?: 'stop' | 'continue' // 解密失败时，默认 stop（fail closed）
}
```

请求侧新增：`selectedProfileId?: string` 与 `cryptoOverrides?`（仅允许覆盖密钥变量名、输出名称、失败策略三项）。

### 2.3 算法集（P1 建议内置）

- 摘要/签名：`MD5`、`SHA1`、`SHA256`、`HMAC-SHA1/SHA256`、`SM3`
- 对称：`AES-128/256-CBC`（PKCS#7 / NoPadding）、`AES-128-GCM`、`SM4-CBC`
- 非对称：`RSA-OAEP`、`RSA-PKCS1v15`、`SM2`

具体先做哪几种，等一份脱敏的接口文档片段（或一次真实请求/响应样例）确认后再收敛，避免实现用不上的算法。

## 3. 界面（三个视图，均已在稿子中画出）

### 3.1 请求视图 · 选方案

- 「加密签名」分区只有一件事：**选方案**（含"不使用签名/加密"），下面是方案摘要 chips 与**只读步骤预览**（每段带「在公共配置里修改 →」）。
- 目录里每条请求显示所用方案（`🔒 后台签名`），一眼看出哪些接口有加密。
- 默认空的「本接口覆盖项」（密钥变量 / 输出名称 / 失败策略），只在个别接口确实不同时使用。
- 状态条显示本次实际形态：`已解密 · AES-128-CBC` / `未解密 · 本地缺少 aesIv` / `本次未加密 · 明文发出`。

### 3.2 公共配置 · 统一管理列表

页签：**变量与密钥 / 签名与加密方案 / 公共请求头 / 公共查询参数 / 公共鉴权**。每个列表都是同一套"四件套"：

| 能力 | 具体表现 |
| --- | --- |
| 查看 | 作用域筛选 + 搜索 + **被引用计数**（点击跳到引用它的请求或方案）+ 按作用域分组 |
| 操作 | 行内 hover 操作（编辑 / 复制 / 删除）、多选批量、导入导出 |
| 编辑 | 表格内联编辑（保存 / 取消）；方案走右侧详情（步骤可拖拽排序） |
| 添加 | 顶部按钮 + 表格底部「＋ 添加一行」+ **批量编辑**（粘贴 `key=value` / `.env`，先预览差异再保存） |

方案页额外要有：**影响面**（"修改这个方案会影响 13 个接口"，保存前二次确认，变更写方案 revision）与**按环境的密钥齐备检查**。变量页额外要有：**删除前引用检查**（`aesIv → 被 1 个方案引用 → 影响 13 个接口`）。

### 3.3 Agent 配置 · 待你补密钥

- 用户一句话 → Agent 提案卡：表格列出"新建方案 / 新建密钥变量（值留空）/ 绑定 N 个接口 / 加公共参数"，并标注哪些**需要用户**。
- 「等你填的密钥」清单：逐行填入值，填完即清空。
- 配置类审批卡明确写：`读密钥：否`、`写密钥：否`、`可回滚 revision`、`发送加密请求时另需一次审批`。

### 3.4 令牌接入（P2 第一项，界面稿 v7 新增）

用户确认的事实：**token 一般来自一次登录请求的响应，且"怎么带 token"是项目级约定**（Header 名可能是
`Authorization` 也可能是 `X-Token`，值可能是 `Bearer {{token}}` 也可能只有 `{{token}}`，还可能放在查询参数或正文字段里）。
因此不能按请求逐条写，必须有项目级配置层。

「令牌接入」也是一条列表（与变量、方案同一套"查看 / 操作 / 编辑 / 添加"交互），每个条目描述一套约定：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| 名称 | 文本 | 例如「后台管理令牌」 |
| 作用域 | 工作区（项目级默认）/ 集合级 | 集合级覆盖工作区，用于同一项目里后台与 APP 两套约定 |
| 放置位置 | 请求头 / 查询参数 / 正文字段 / Cookie | 决定 token 出现在哪里 |
| 字段名 | 文本 | 例如 `Authorization`、`X-Token`、`token` |
| 值模板 | 模板串 | `Bearer {{sessionToken}}`、`{{appToken}}` 或自定义（支持固定前缀与多变量拼接） |
| token 来源 | 登录接口提取（接口 + 路径，如 `POST /admin/v1/login → data.token`）/ 手填变量 / 外部提供 | 提取走既有 `ApiExtraction`（`json` / `header` / `sse-last-data`） |
| 来源缺失时 | 照常发送（不带该字段）/ 跳过该请求 | 默认照常发送，与「缺密钥不阻断」保持一致 |

交互契约：

- 请求页不重复配置，只显示一条继承条：`由「后台管理令牌」继承 · Authorization: Bearer {{sessionToken}}`，并提供「查看 / 覆盖 →」。
- 接口自带同名 Header 时以接口为准，并给黄标提示，避免两套约定打架。
- 影响面：显示「继承 218 个请求 / 其中 12 个自带 Authorization / 集合级覆盖 2 处」，改前二次确认。
- Agent 可代配这套结构（名称、位置、字段名、模板、来源接口与路径、作用域），**但 token 值仍然只能来自登录提取或用户手填**，Agent 读不到也写不了值。

这一层刻意与 §2.3 的签名/加密方案分开：**鉴权是"带什么凭据"，加解密是"报文怎么变形"**，两者都可能改 Header，但混在一起会让影响面与审批边界说不清。
界面稿见 `docs/superpowers/specs/2026-09-26-api-workbench-crypto-ui.html`（v7，「公共配置 → 令牌接入」页签）。

## 4. 执行语义

1. **顺序即语义**。签名签的是明文还是密文，取决于它排在加密钩子之前还是之后，两种接口都存在，因此步骤用编号显式排序，不做隐式固定。
2. **缺密钥绝不阻断**（用户决策）。本地无法判断服务端到底验不验签名；阻断等于用本地假设替服务端做决定——如果生产的服务端本来不需要密钥，接口就永远发不出去。缺哪一步就跳过哪一步，**照常发送，服务端返回什么就显示什么**。
3. **代价用可见性补，不用阻断补**。缺步骤必须在三处显式标注：① 请求状态条（`本次未加密 · 明文发出（缺 aesKey / aesIv）`）② 运行记录 ③ Agent 审批卡；运行历史可按「明文发出」筛选。目的：避免"以为加密了，其实发的是明文"。
4. **解密失败分类**，不用一句"失败"糊过去：① 本地缺密钥 → 标「未解密」，密文原文照常可查；② 有密钥但解不开 → 「解密失败 · 密钥不匹配（填充无效）」；③ 不是密文 → 提示先看状态码与 Content-Type。失败默认**跳过断言**，但保留密文原文与"临时指定密钥重试"入口。
5. **断言与提取跑在解密后的原始正文上**（不是脱敏后的投影）。这条是既有教训：曾出现提取跑在脱敏结果上，`{"token":"..."}` 被遮罩成 `[REDACTED]`，等于提取到假值。
6. **兼容既有能力**：Cookie Jar、SSE、multipart、用例、场景流程、运行对比都按同一套钩子链路跑；场景流程里每个步骤用各自方案。
7. **记录内容**：算法名、方案名与 revision、密钥引用名、实际发出的密文与变形前明文（沿用现有加密产物策略）、实际使用的 `timestamp` / `nonce`（非秘密，便于复现）。**密钥值永不记录**。

## 5. 安全与边界

- **密钥值只来自环境变量**，走现有 `safeStorage` 密文存盘；方案与请求定义里只出现变量名。写进请求定义会跟着集合快照导出泄漏（导出只把秘密替换成占位符，前提是秘密存在环境里）。
- **明文显示策略（用户决策）**：测试/本地默认明文可见；**生产默认遮蔽**，点 👁 才显示并留审计。无论哪种状态，三条不变量不变：**不进运行记录、不进日志、导出快照只导占位符**。
  - 代价已知并接受：明文显示期间，截屏、录屏、远程协助会连密钥一起暴露；因此生产默认遮蔽、显示行为留审计。
- **Agent 权限边界（用户决策）**：Agent 可以配置结构——新建/修改方案、创建变量名与类型（秘密变量值留空）、维护公共请求头与参数、给接口批量绑定方案；**读不到、写不了、覆盖不了任何密钥值**，工具返回里只有 `secret: true / configured: false` 这类事实。
- **两次独立审批**：① 配置类动作（改方案/建变量/绑定接口，一次审批，展示影响面）；② 真正发送加密请求（另一次审批，那次才会读取密钥）。两者分开，保证"配错方案"和"拿密钥发请求"可分别审计。
- **生产明文发出必须留痕**：按 §4.3 在状态条与运行记录标注，历史可筛选。

## 7. 验证策略

- 纯函数单测：算法正确性（对齐公开测试向量）、拼串模板求值、顺序语义（签名在加密前后）、失败分类、缺密钥跳过。
- 真实 Electron 端到端（扩展 `scripts/api-workbench-smoke.ts`）：本地夹具端点提供「验签 + AES 加密 + 加密响应」，覆盖：① 签名与服务端一致 ② 响应解密后可断言与提取 ③ 缺密钥时明文发出且状态条/记录标注 ④ 运行记录里搜不到密钥值与明文密钥 ⑤ Agent 工具拿不到密钥值（返回体断言）。
- 界面 smoke（扩展 `scripts/api-workbench-ui-smoke.ts`）：三个视图的渲染与交互断言——方案选择与只读步骤、管理列表四件套、变量"待填写"状态、配置类审批卡文案、缺密钥状态条、明文/遮蔽切换与审计。

## 8. 分期建议

- **P1（先做，能立刻用）**：变量与密钥管理列表（含作用域、秘密标记、批量编辑、引用检查）+ 签名与加密方案管理 + 接口选方案 + 发送/接收执行 + 缺密钥标注与明文发出留痕。
- **P2**：公共请求头 / 公共查询参数 / 公共鉴权三个列表 + 接口"生效来源"展示 + 运行历史按「明文发出/未解密」筛选。
- **P3**：受限表达式 DSL（覆盖非标拼串签名）、国密与证书类算法补充、方案导入导出。

## 9. 未决与风险

- 算法最终清单取决于真实接口文档；本文档 §2.3 是建议集，不是承诺。
- 生产"明文发出"虽然留痕，但仍可能把业务数据以明文送到服务端——这是用户明确选择的行为（不阻断），需在界面上持续可见。
- 密钥值明文显示扩大了暴露面（截屏/录屏/远控），已用"生产默认遮蔽 + 审计"收敛，但无法完全消除。
- 方案是共享资产，改错的爆炸半径大；用「影响面二次确认 + revision + 运行记录绑定 revision」缓解，不承诺自动回滚。
